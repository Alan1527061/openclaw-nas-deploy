# 踩坑记录

> 都是本人部署/使用 OpenClaw 过程中真实踩过的坑，每条按「现象 → 排查 → 原因 → 解决」记录。
> 面试被问项目时，这页是你「真动手」最有力的证据——能讲出这些，比背一百条概念都硬。

---

## 坑 1：Control UI 外网打不开，浏览器报 `origin not allowed`

- **现象**：在外网（或换了新端口/IP）访问网页控制台，页面打不开，浏览器提示 origin 不被允许。
- **排查**：先查是不是网络/反代问题——内网 IP 直连正常，但用域名或改端口后就报错；对比发现是**访问来源地址变了**。
- **原因**：OpenClaw 的 `controlUi.allowedOrigins` 是**逐字比较**「协议 + host + 端口」的白名单。新增一个访问入口（域名、IP、端口任一变化），只要不在白名单里，浏览器就会被拒。我一开始只配了内网 IP，后来加 dynv6 域名走 IPv6 反代就触发了这个报错。
- **解决**：把实际会用到的每个访问入口（公网域名 `https://alan152.dynv6.net:18888`、内网 `http://192.168.0.119:18888` 等）都**逐字**加进 `openclaw.json → gateway.controlUi.allowedOrigins`，然后 `docker restart openclaw`。
- **教训**：OpenClaw 的安全校验是「来源白名单 + token」双层，白名单做的是字面精确匹配——以后任何入口变化，第一反应先查这里。

## 坑 2：宿主机上改不动 OpenClaw 的配置文件

- **现象**：想直接在 NAS 上用 `vi` 改 `config/openclaw.json`，保存时提示没权限；直接编辑文件总是不生效。
- **排查**：查文件属主和权限，`ls -l` 显示属主是 `1000:1000`、权限 `600`；而宿主机当前登录用户不是 1000 号用户。再对比：容器里的 openclaw 进程（以 node 用户运行，UID 1000）却能正常读写。
- **原因**：容器运行时用户是 `node`（UID 1000），而 OpenClaw 以该用户身份往配置文件回写状态。宿主机上用非 1000 用户去改，权限对不上；强行改坏还会导致容器内进程读写异常。
- **解决**：配置文件的管理要**顺着容器来**——要么 `docker exec` 进容器内改，要么把宿主机文件属主调整为 `1000:1000`（并保持权限 `600`），改完 `docker restart openclaw`。
- **教训**：Docker 挂载目录的「宿主 vs 容器」权限边界很绕，凡是容器内进程要读写的文件，统一用容器内的用户视角去管理，别在宿主机硬改。

## 坑 3：飞书里和机器人对话，OpenClaw 发不出图片/部分消息

- **现象**：在飞书里跟「小龙虾」聊天，文字回复正常，但让它发图片（或某些富媒体）时没反应或报错。
- **排查**：先看 `docker logs`，没有模型调用错误；再检查 OpenClaw 侧配置没问题。最后想到飞书侧权限——去飞书开放平台的应用配置里核对权限。
- **原因**：飞书机器人**能收发文本**只需要基础能力，但「发图片、发文件、发富媒体卡片」这类能力需要在**飞书开放平台**给应用**单独开启对应权限**（scope）。没开权限时，OpenClaw 底层调用飞书 API 会被拒。
- **解决**：飞书开放平台 → 你的应用 → 权限管理，把机器人发送图片 / 文件等所需的权限开起来，发布新版本生效后重试。
- **教训**：接飞书这类平台机器人，「消息能通」和「各种消息类型都能通」是两码事——能力被平台侧权限卡住时，先别怀疑自己代码，去开放平台核对 scope。
